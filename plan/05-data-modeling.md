# Фаза 4. Моделювання даних

Ціль: нормалізація 1NF–BCNF, ключі й зв'язки, коли денормалізувати, generated columns, ENUM vs lookup, спроєктувати e-commerce схему з нуля і захистити рішення.

---

## 4.1. Нормалізація (вміти пояснити своїми словами)

- **1NF:** атомарні значення, немає повторюваних груп / масивів "замість таблиці". Кожна клітинка — одне значення.
- **2NF:** 1NF + кожен неключовий атрибут залежить від **усього** складеного ключа, не від частини. (Актуально лише при складеному PK.)
- **3NF:** 2NF + немає транзитивних залежностей (неключовий атрибут залежить лише від ключа, не від іншого неключового). Приклад порушення: в `orders` тримати `customer_email` — воно залежить від `customer_id`, не від `order_id`.
- **BCNF:** для кожної функціональної залежності `X → Y` ліва частина `X` — суперключ. Трохи строгіше за 3NF; на практиці різниця рідкісна.
- Далі 4NF/5NF — знати назви й що це про багатозначні залежності / join-залежності; на співбесіді достатньо BCNF.

Практичне правило: **проєктуй у 3NF/BCNF, денормалізуй свідомо й точково під конкретний запит, документуючи чим підтримуєш узгодженість.**

**Вправа 4.A:** знайди в `sandbox/schema.sql` місця свідомої денормалізації (`orders.total_cents`, `order_items.unit_price_cents`, `products.search_title`, `customers` без окремої таблиці імен). Для кожного: яку залежність порушено, який запит це прискорює, як тримати консистентність (тригер? застосунок? періодичний перерахунок?). Запиши в `notes/04-denorm.md`.

## 4.2. Ключі

- **Natural key** — має бізнес-сенс (`sku`, `email`, ISO-код країни). Плюс: не потребує join для людського читання. Мінус: змінюється, буває довгим/складеним, витікає в FK усюди.
- **Surrogate key** — штучний (`bigint IDENTITY`, `uuid`). Плюс: стабільний, компактний, однорідний. Мінус: не несе сенсу, потребує unique-обмеження на natural key окремо.
- Практика: surrogate PK (`bigint`) + `UNIQUE` на natural key. Ми так і зробили.
- `bigint` vs `uuid` як PK: `uuid` глобально унікальний (мерджі, offline-генерація), але 16Б, випадковий → погана локальність B-tree, роздування WAL, повільніші вставки на великому обсязі. `uuidv7` (час-сортований) знімає більшість мінусів. Обговоримо детально у фазі 6.
- Складений PK доречний для таблиць-зв'язок (`order_items(order_id, line_no)`, `coupon_redemptions(coupon_code, order_id)`).

## 4.3. Зв'язки

- **1:1** — рідко; або та сама таблиця, або винесення необов'язкової/рідко потрібної частини (`orders` ↔ гіпотетична `order_gift_wrap`). FK + `UNIQUE` на ньому.
- **1:багато** — FK на стороні "багато" (`addresses.customer_id`). 90% зв'язків.
- **багато:багато** — таблиця-зв'язок (junction) зі складеним PK. Може мати власні атрибути (`coupon_redemptions.redeemed_at`, `order_items.qty`).
- **самопосилання** — `categories.parent_id → categories.id` (дерево). Альтернативи зберігання ієрархії: adjacency list (у нас), materialized path (`text`/`ltree`), nested sets, closure table. Знати компроміси (швидкість читання піддерева vs складність запису).

## 4.4. ENUM vs lookup-таблиця

У схемі навмисно є обидва: `payment_status` — `ENUM`, `order_statuses` — таблиця.

| | `ENUM` (`CREATE TYPE ... AS ENUM`) | Lookup-таблиця |
|--|-----------------------------------|----------------|
| Додати значення | `ALTER TYPE ... ADD VALUE` (не в транзакції до PG12; не можна видалити/перейменувати легко) | звичайний `INSERT`/`UPDATE`/`DELETE` |
| Додаткові атрибути (сортування, прапорці, локалізація) | ні | так (`sort_order`, `is_terminal`) |
| FK-цілісність | вбудована в тип | через `REFERENCES` |
| Місце / швидкість | 4Б, дуже швидко | `text` + FK, join для атрибутів |
| Порядок | порядок оголошення | твій `sort_order` |
| Міграції | болючіші | простіші |

Відповідь на співбесіді: **`ENUM` — для маленького, стабільного, суто технічного набору (`payment_status`); lookup-таблиця — коли значення можуть додаватися бізнесом, потрібні атрибути/сортування/локалізація/аудит (`order_statuses`).**

**Вправа 4.C:** додай новий статус `on_hold` кожним способом: `ALTER TYPE payment_status ADD VALUE 'on_hold' BEFORE 'failed'` і `INSERT INTO order_statuses`. Відчуй різницю. Потім спробуй "видалити" значення enum — переконайся, що це боляче.

## 4.5. Generated columns, домени, CHECK-и як частина моделі

```sql
-- у нас: products.search_title text GENERATED ALWAYS AS (lower(title)) STORED
ALTER TABLE shop.order_items
  ADD COLUMN line_total_cents int GENERATED ALWAYS AS (qty * unit_price_cents) STORED;

CREATE DOMAIN shop.email_t AS citext CHECK (VALUE ~ '^[^@]+@[^@]+\.[^@]+$');
CREATE DOMAIN shop.positive_int AS int CHECK (VALUE > 0);
```
- `GENERATED ... STORED` — обчислюється при запису, займає місце, можна індексувати як звичайний стовпець. `VIRTUAL` з'явився в PG18 (обчислення при читанні) — перевір і спробуй.
- `DOMAIN` — іменований тип з обмеженнями, перевикористання правил валідації.
- Табличний `CHECK` може посилатися на кілька стовпців того ж рядка (`CHECK (delivered_at IS NULL OR shipped_at IS NOT NULL)` у нас).

**Вправа 4.D:** додай `line_total_cents` як generated stored, перепиши пару запитів з фази 2 через нього, порівняй читабельність і `EXPLAIN`.
